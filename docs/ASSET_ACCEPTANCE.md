AudioWorklet 連續擷取推翻前述「沒有全靜音窗」的弱證據：新增 `web_audio_capture_test.js`，在獨立音訊執行緒逐樣本檢查送往 destination 的混合輸出，觀察分支輸出保持零，避免音量加倍。Chrome 153／48 kHz、兩模式各約 30.1 秒，涵蓋 26 秒循環與首次進出屋。預設 Sample 最長低於 0.00001 的連續區段只有 1 個樣本（0.0208 ms）；Stream 在約第 26.219 秒測得 170.667 ms，對應首次進屋操作。兩路無執行或擷取錯誤，Stream 屋內截圖已确认實際進入花園小屋。決策：不將 Stream 改為預設，保留診斷開關與重現工具；先前單執行緒輪詢無法排除斷音的警告已被實測證實。仍未證明個別環境音循環接縫不可聞，因為混合輸出可被音樂遮蔽；也不是所有瀏覽器或長時間音訊品質驗收。

延長後端比較：兩種模式的村莊各增加 26 秒循環觀察與首次進屋／返回村莊指令，另保留完整戰鬥回合。Chrome 153 四路皆無執行錯誤或滿刻度樣本；村莊循環階段左右各 2600 個觀察窗均非全靜音，兩模式 RMS 約 0.0152／0.0153。進出屋與戰鬥取樣亦未發現全靜音窗。這不能排除短間隙：2048 樣本窗可能跨過短斷音，主執行緒卡頓期間觀察器本身也停止取樣（首次進屋 2 秒僅 173／178 窗，未滿約 200 窗）。因此沒有足夠證據把正式預設改為 Stream；保留測試開關，後續若要判定負載下的無縫程度需獨立音訊執行緒擷取或實際錄音，而非再增加主執行緒輪詢。截圖時間戳 `1789905061307` 至 `1789905129290`。

播放後端定位：檢查目前匯出的 `index.js`，Sample 節點在 `ended` 回呼執行 `restart()` 並重建 source，而非使用原生 source.loop；與已量測晚接現象相符。加入僅限 Web 且需明確參數 `--stream-loop-audio` 的診斷模式，只把 Music／Ambience 播放器改為 Stream，正常設定與 SFX 不變。`web_mix_test.js` 已比較兩模式的村莊與戰鬥短路線：四路均有输出、無 runtime 錯誤或觀察到滿刻度样本，背景 RMS 相近（約 0.015）。此短測未越過全部循環邊界、未涵蓋切圖卡頓下的 underrun，不能宣稱 Stream 已解決循環問題，也未作為正式預設。官方 [Audio streams 說明](https://docs.godotengine.org/en/stable/tutorials/audio/audio_streams.html) 提醒單執行緒 Web 使用 Sample 可避免串流音訊失真；該頁亦標示尚未針對 4.7 更新，因此以本地匯出與實測作主要依據。

瀏覽器循環排程補驗證：`web_audio_test.js` 記錄 Web Audio 時鐘、start 時間／offset／播放倍率，在取樣結束後逐樣本比對相同 PCM（後端循環會建立新 AudioBuffer）。Chrome 153 村莊音樂一個接點排程差為 0 ms；環境音兩個接點分別晚接約 4.0／9.3 ms，沒有提前排程餘裕。原有解鎖、靜音、恢復、對話與再次播放檢查通過，無 runtime 錯誤。這表示原始音檔通過接點檢查，仍不能宣稱 Web 循環無縫；短環境音重播存在排程間隔，待比較播放後端方案。數值是 API 排程時間，不是錄製聲波或聽感結論；尚未涵蓋遺跡／戰鬥配樂、所有瀏覽器或長時間負載。

六段循環 PCM 接點檢查已加入既有 `audio_asset_test.py` 並通過：三段立體聲配樂及三段單聲道環境音均為 32 kHz／16-bit，逐聲道檢查完整度、無滿刻度樣本、DC 偏移低於 0.001、首尾相邻樣本跳變低於 0.02。實測接點差值為 151–486／32768；首尾各 100 ms RMS 比值約 0.91–1.81，均有訊號且不超過 2 倍差異。這些為偵測明顯檔案回歸的工程門檻，不是「聽不出接點」的證明；原始配樂已把尾音繞回開頭，不應強制首尾歸零。音檔未修改，瀏覽器排程間隙與音樂句法仍待驗收。既有 PCM 清單項目現在包含 3 組 unittest，統一清單總數仍為 53。
